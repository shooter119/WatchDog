# WatchDog 剩余问题归类与自动整改授权

更新时间：2026-08-29

## 1. 统一处理规则

用户已明确授权：凡是不直接改变 App 界面、页面流程、用户操作方式或产品体验的事项，主 Agent 直接制定方案、登记待办、实施、测试和验收，不再逐条询问技术细节。

只有以下事项保留用户讨论环节：默认入口、页面布局、按钮/手势、录音时长提示、低存储提示、失败后的用户操作路径等会直接改变使用体验的产品取舍。

本文件是对[主问题台账](consolidated-ledger.md)的执行分类。原台账中的代码行、复现证据、根因和涉及文件继续作为问题证据；本文件只补充处理授权、统一方案和执行顺序，不把“已纳入待办”误写成“已修复”。

## 2. A 类：主 Agent 直接整改，不再讨论

### A1. 身份、RBAC 与单位隔离

问题：`BACK-001`、`BACK-003`、`BACK-004`、`SEC-003`、`SEC-004`、`SEC-005`、`SEC-019`。

统一方案：保留“单位 + 姓名 + 验证码”的低摩擦入口；服务端增加单位成员白名单、实名绑定、会话签发、角色和设备撤销；普通成员与管理员分权；所有业务请求从服务端会话取得 `unit_id`，不信任客户端 header/profile；`unit_id=NULL` 历史数据默认隔离，建立可审计的管理员认领流程；操作日志和高影响管理接口纳入角色控制。

执行顺序：先完成数据模型和接口契约，再完成兼容认证、管理员路径、会话撤销和旧客户端窗口，最后做跨单位/冒用/越权回归。

### A2. 数据一致性、幂等、迁移与 RLS

问题：`BACK-006`、`BACK-007`、`BACK-009`、`BACK-010`、`BACK-015`、`BACK-018`、`SEC-015`、`SEC-016`、`TQ-008`、`DB-LOCAL-001`～`DB-LOCAL-004`、`DB-EXT-001`～`DB-EXT-003`。

统一方案：使用 `(unit_id, client_op_id)` 操作账本；PostgreSQL 使用事务/RPC、数据库锁和条件更新；SQLite 使用 `BEGIN IMMEDIATE` 保持同一契约；增加外键、CHECK、索引和迁移版本/校验和；生产禁止 SQLite 回退；readiness 在数据库、迁移和最小读写未通过时返回 503；RLS、受限角色/RPC 和 API 单位过滤形成纵深边界。

第六轮数据库复核已自动闭合 `DB-LOCAL-001`（旧库重复启动不再重复建档）、`DB-LOCAL-003`（兼容迁移纳入事务回滚）和 `DB-LOCAL-004`（原子 RPC 开关强制依赖操作账本），并新增 `008_atomic_rpc_conflict_index.sql` 处理 `DB-LOCAL-002`；`DB-LOCAL-002` 的真实 PG DDL/RPC 调用、以及 `DB-EXT-001`～`DB-EXT-003` 仍按外部验收条件保留。

执行顺序：只读扫描历史数据 → 兼容迁移和版本记录 → 双驱动契约测试 → 真实 PostgreSQL 双实例并发验证 → 备份恢复和重启扩容演练。任何异常历史数据均不自动删除、不猜测归属。

### A3. 限流、输入资源和隐私日志

问题：`BACK-002`、`BACK-012`、`BACK-013`、`BACK-014`、`SEC-006`、`SEC-007`、`SEC-008`、`PE-018`、`LOG-SEC-001`。

统一方案：CloudBase 网关负责多实例共享限流，后端保留进程内止损；按来源、单位、接口和资源类型限额；不以客户端设备 ID 作为唯一依据；所有请求关联 `request_id/op_id`；输入字段、音频、解析、聊天和上游响应均有长度/并发/超时上限；技术日志只保留白名单字段，ASR/LLM 原文、Token、验证码、名单和完整异常不进入技术日志；诊断上报使用允许字段清单。当前生产默认 `/` 路由已配置资源总量 100 QPS；客户端维度与多实例压力校准继续列为外部验收。

### A4. 出站目标、设备标识与本地存储

问题：`SEC-009`、`SEC-010`、`SEC-011`、`SEC-012`、`SEC-013`、`SEC-017`、`SEC-020`。

统一方案：生产外部服务只允许登记的 HTTPS 主机和受控重定向；正式 App 不向任意地址发送生产凭据；稳定硬件指纹替换为随机安装 ID 与服务端设备句柄；Token/会话进入安全存储，现场缓存采用应用级加密；ASR 模型采用签名 manifest、SHA-256 和原子替换；密钥与诊断包不落明文；生产主机和 CI secret 权限纳入部署检查。

### A5. 查询、轮询和资源效率

问题：`BACK-016`、`PE-004`、`PE-006`、`PE-007`、`PE-010`、`PE-011`、`PE-013`、`PE-017`、`PE-019`、`PE-MODEL-001`、`PERF-RATE-001`、`ASR-CACHE-001`。

统一方案：警情列表服务端分页、稳定排序和有限投影；参战力量批量读取；普通 GET 不触发归档等写操作；归档严格按单位和状态条件执行；合并前台/后台轮询责任并增加退避；每秒告警 tick 与页面重建解耦；日志采用批量/队列写入；旧模型 generation 有限保留并在低存储时安全清理；依赖升级放入维护窗口并保留回归门禁。

### A6. 发布、容器和工程流程

问题：`BACK-017`（已代码级闭合，继续保留部署复验记录）、`BACK-019`、`BACK-021`、`SEC-014`（已闭合，转入定期审计）、`SEC-018`、`TQ-001`、`TQ-002`、`TQ-012`、`PE-R3-001`、`FLT-021`、`DEPLOY-001`、`CI-SEC-001`、`CI-OTA-001`、`CI-OTA-002`。

统一方案：生产部署健康检查绑定实际目标；容器非 root、HEALTHCHECK 和最小权限；Action 固定提交 SHA；main、workflow、tag、Release 和签名 secrets 受保护；质量门禁检查 backend/App 数量、skipped/todo、analyze、测试、版本、ABI、签名和 SHA256；缺签名不产出正式包。国内 OTA 必须先完成专用 PG Storage bucket/RLS/API key 配置与 APK/清单远端校验，再创建 GitHub Release，避免半完成发布；App 和 workflow 统一使用 `...api.tcloudbasegateway.com/v1/storages/object/public/{bucket}/{object}`，旧 `/ota/*` 仅保留严格白名单兼容重定向；CloudBase 服务详情只允许字段过滤输出，敏感环境变量不进入终端记录；必要的密钥轮换由运维按影响评估执行。

第十九轮已按该方案完成质量、版本、ABI、签名和 GitHub Release 兜底；CloudBase 对象上传仍在多个递增 tag 和多种请求路径上失败，已登记为 `CI-OTA-002` 外部阻塞，未把人工 Release 误记为 OTA 验收通过。

### A7. 测试和外部环境验证

问题：`TQ-003`、`TQ-004`、`TQ-005`、`TQ-006`、`TQ-010`、`TQ-011`，以及 `FLT-004`、`FLT-006`、`FLT-009`、`FLT-013`、`FLT-015`、`PE-003`、`PE-014`、`PE-015`、`UI-UX-004`、`UI-UX-005` 的真实环境验证部分；`TQ-007`、`TQ-009` 已由 ApiClient 与管理页面回归闭合。

统一方案：补齐 ASR/parse/ApiClient/管理端点契约测试；在隔离环境验证真实同步、离线队列、录音权限、本地 ASR、报警/TTS/前台服务、网络超时和生命周期；用真实 Android 设备验证 TalkBack、减少动效、锁屏、备份恢复、低存储和插件行为；覆盖率和测试稳定性作为工程门禁，不改变业务规则。

这些事项虽然涉及 App 或设备，但属于对已确定行为的技术验证，不需要用户作产品选择；主 Agent 直接安排并在阶段汇报中报告结果。

## 4. 统一执行顺序

1. A1 身份/RBAC/单位隔离与 A2 数据一致性、生产持久化保护。
2. A3 敏感日志、输入资源和共享限流。
3. A4 出站目标、本地安全存储、设备标识和模型完整性。
4. A5 查询放大、轮询、电量、内存和日志写入效率。
5. A6 发布、容器、仓库权限和部署门禁。
6. A7 真实 PostgreSQL、CloudBase、Android 设备和上游服务验证。
7. B 类前端事项按用户体验确认后实施，随后进行完整回归和最终验收。

## 5. 汇报方式调整

后续阶段汇报不再逐条询问后台技术方案，而是按“已自动归类的问题、已完成修复、验证结果、仍需外部证据、需要用户决定的体验事项”汇总。所有修改前先协调文件归属，所有修改后执行 AGENTS.md 要求的 backend/App 验证；涉及 backend 或 deploy 的改动在验证通过后按项目约定部署。
