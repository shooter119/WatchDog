## 下一项讨论：数据一致性与并发

对应问题：`BACK-006`、`BACK-009`、`BACK-010`。

重点讨论：

- 业务状态与事件时间线是否必须由同一数据库事务提交；
- 离线补传的 `client_op_id` 是否需要独立 operation ledger；
- 多实例新建警情的冷却、编号、建档事件如何用唯一约束或 PostgreSQL RPC 原子化；
- 自动归档、活动时间更新和事件写入的并发胜者规则；
- SQLite 与 PostgreSQL 是否必须保持完全一致的事务语义；
- 迁移失败、重复提交和部分故障时的回滚与重试行为。

在上述规则确认前，不改动生产数据库结构，不进行不可逆迁移。

## 已确定的数据库改造方案

用户已授权主 Agent 直接制定数据库修改方案，不再逐项询问数据库技术细节。本方案默认采用安全优先、向后兼容、可回滚的实现。

### 1. 操作账本

新增 `operation_ledger`，以 `(unit_id, client_op_id)` 作为唯一键，保存操作类型、警情、规范化请求摘要、操作者/设备、成功结果和时间信息。初版不自动清理操作账本，避免过期重试再次产生重复业务记录；后续只有在确认数据保留策略和迁移工具后才增加归档。

相同操作 ID 的处理规则固定为：请求摘要一致则返回第一次成功结果；摘要、警情或操作类型不一致则返回 409；事务失败不留下成功账本记录，客户端可以安全重试。

### 2. PostgreSQL

新增数据库迁移和事务 RPC，不在 Node.js 中用多次 PostgREST 请求拼接伪事务。优先实现：

- `rpc_create_incident`：单位级锁、冷却检查、唯一编号、警情、建档事件和操作结果一次提交；
- `rpc_apply_incident_operation`：进场、出场、压力复核、随手记的业务状态、采样、事件、活动时间和操作结果一次提交；
- `rpc_archive_incident`：条件归档、未离场人数、归档事件和操作结果一次提交；
- `rpc_apply_offline_operation`：每条离线操作独立事务，批量请求不因单条坏数据整体回滚。

新增/调整的数据库约束包括操作账本唯一键、事件操作作用域和必要索引；迁移只增加字段、表、索引和函数，不删除历史数据，不自动认领 `unit_id = NULL` 的旧警情。

### 3. SQLite

在 SQLite driver 增加与 PostgreSQL 相同语义的事务封装，关键操作使用 `BEGIN IMMEDIATE`。SQLite 与 PostgreSQL 必须共享相同的重复、冲突、回滚和返回值契约，不能只验证模拟数据库。

### 4. 应用与接口兼容

保留现有 REST endpoint 和响应主体；由后端适配器内部切换到事务/RPC。新版本 App 对关键写操作统一生成稳定 `client_op_id`；旧客户端在兼容窗口内继续可用，但记录兼容告警，待新版本覆盖率达到要求后关闭无幂等 ID 的关键写入。

### 5. 重点验收

必须在真实 PostgreSQL 预生产环境使用两个服务实例验证：同一操作并发请求只产生一条业务记录和一条事件；故障注入不会留下半成品；新建警情冷却不会双建档；归档不会重复写事件；乱序活动时间取最大值；跨单位/跨警情/跨类型复用操作 ID 返回 409。SQLite 运行同一组契约测试。

### 6. 发布与回滚

先执行数据库备份/快照和 dry-run，再发布兼容迁移，随后发布支持事务 RPC 的后端，最后打开功能开关并做灰度。回滚只回退应用版本，不删除迁移对象；保留新增表、函数和字段，确保旧版本仍能启动。生产迁移失败时停止发布，不自动执行破坏性修复。

## 已确认计划：`BACK-015` 数据库外键与关键业务约束

问题证据：当前 PostgreSQL 与 SQLite schema 对 `incident_events.incident_id`、`incident_forces.incident_id`、`pressure_samples.entry_id` 主要使用普通文本字段，没有完整外键；压力、耗气率、计数等关键不变量也主要依赖路由代码。数据库维护脚本或未来接口一旦绕过路由，可能产生孤儿事件、孤立参战力量、孤立压力采样或非法计算参数。

建议采用“先盘点、再加约束；保留历史、拒绝新增坏数据”的方案：

1. 先对 SQLite 和 PostgreSQL 做只读孤儿记录、非法状态和非法数值扫描，生成迁移前报告；扫描结果不写入生产数据。
2. 先补齐索引和应用层统一校验，明确 `incident_events`、`incident_forces`、`pressure_samples` 的父子关系，以及容量、耗气率、压力、人数和状态枚举的合法范围。
3. PostgreSQL 采用分阶段迁移：新增约束时先使用兼容历史数据的方式登记，校验通过后再正式验证；不直接删除或自动归属历史异常记录。
4. SQLite 在确认历史数据通过预检后重建相关表，开启外键约束并保留原数据；迁移失败时保留旧库副本并中止切换。
5. 删除策略默认采用 `RESTRICT` 或业务归档，不使用级联删除，避免删除警情时连带清除事件和压力历史；如现有功能要求删除，改为软删除/归档并保留审计链。
6. 对无法自动修复的旧数据建立异常清单或隔离记录，交由明确的管理流程处理，不在迁移中猜测归属、不覆盖原始数据。
7. 增加双驱动契约测试：非法外键、非法数值、非法状态、父记录删除、重复迁移、事务失败和迁移后读写均必须得到一致结果。

验收条件：迁移前有完整扫描结果；新增写入不能产生孤儿或非法数值；历史合法数据完整保留；异常历史数据不会被静默删除；SQLite 与 PostgreSQL 的约束和错误语义一致；迁移可重复执行、失败可恢复，并通过后端全量测试。

## 施工记录：`BACK-018` 数据库迁移版本与失败恢复

问题证据：`backend/scripts/migrate-cloudbase.js` 当前按文件名读取 SQL 并逐条调用 CloudBase 数据库接口，没有 `schema_migrations` 版本表、文件校验和、并发迁移锁或整体事务边界。网络中断、权限失败或单条 DDL 出错后，前序语句可能已生效，重跑时也无法明确判断数据库处于哪个结构版本。

建议采用“版本化、校验、单向兼容、失败可识别”的方案：

1. 新增迁移记录表，保存迁移版本、文件名、规范化 SQL 校验和、开始/完成时间、执行器和状态；已应用迁移文件禁止原地修改，只能新增更高版本。
2. 迁移运行前读取当前版本，按明确顺序只执行待应用版本；已完成且校验和一致的版本跳过，校验和不一致立即停止并报警，不能默默重跑不同内容。
3. 优先将每个迁移版本作为一个数据库事务执行，并在迁移前取得数据库级互斥锁；若 CloudBase 接口不支持跨语句事务，则使用单个数据库函数/SQL block 或可恢复的分阶段迁移状态，明确记录已完成步骤，禁止伪装成原子迁移。
4. 迁移脚本只做向前兼容的增量操作，先增加结构和兼容字段，再切换后端读写，最后才考虑约束验证；不提供未经确认的 destructive down migration，不删除历史数据。
5. 增加 preflight/dry-run：检查数据库连接、当前版本、迁移文件完整性、目标权限和应用兼容窗口；发现版本跳跃、未知版本、校验和不匹配或半完成状态时停止发布。
6. 部署顺序固定为迁移预检、兼容后端发布、迁移执行/验证、功能开关和灰度；迁移失败时保留现场和状态记录，回滚应用版本，不删除已创建的表、字段或函数。
7. 在隔离 PostgreSQL 环境测试首次安装、重复执行、中途断网、权限失败、并发执行、校验和篡改、半完成恢复和旧后端兼容；SQLite 迁移也纳入同一版本/结果契约检查。

验收条件：迁移状态可查询、版本顺序明确、同一版本内容不可悄悄改变；成功迁移可安全重复执行；失败后能识别已完成步骤并继续或停止；并发迁移不会互相覆盖；应用不会在不兼容 schema 上接收流量；生产历史数据和旧结构不被自动删除。

## 下一项讨论：`SEC-016` PostgreSQL RLS 与租户纵深隔离

问题证据：数据库侧虽已启用 RLS，但缺少按单位的 SELECT/INSERT/UPDATE/DELETE 策略；运行时若继续使用 service role，RLS 也可能被绕过，当前隔离主要依赖 `server.js` 和 driver 的单位过滤。该防线不足会让未来接口、维护脚本或 PostgREST 权限配置错误扩大为跨单位访问。

建议采用“服务端身份先行、数据库策略纵深保护、全局表单独处理”的方案：

1. 以认证会话中服务端确认的 `unit_id` 作为唯一租户上下文，不信任客户端 `X-Scene-Code`、profile 或设备头作为数据库权限依据；旧 `unit_id=NULL` 数据默认拒绝业务可见，不自动认领。
2. 区分表的隔离范围：警情、参战力量、事件、压力采样、操作日志和聊天记录按单位隔离；全局共享的消防员名单/热词保持既定共享规则，不套用错误的单位策略。
3. 为运行时建立受限数据库角色或受控 RPC 边界，应用不直接获得任意表 DML；数据库函数只接受经验证的会话上下文，写入的 `unit_id` 必须由服务端/数据库上下文决定，不能由请求正文自由指定。
4. 为所有单位范围表增加 RLS 策略，覆盖读取、新增、修改和删除；策略同时约束目标行和新行，防止通过 UPDATE 把记录改到另一单位。service role 仅用于迁移/受控管理，不作为普通业务读写角色。
5. 若 CloudBase 当前接口无法传递可靠 JWT/租户上下文，则先把 API + RPC 作为强制边界，并在部署验收中明确记录“RLS 未作为唯一防线”；待平台支持受限角色后再启用完整策略，不伪称已完成数据库隔离。
6. 将跨单位访问、跨单位写入、单位切换、NULL 历史记录、管理员路径、PostgREST 直接访问和 service role 配置纳入预生产安全测试；失败时返回统一拒绝，不泄露目标单位是否存在。
7. 将 RLS 策略、角色授权、函数权限和迁移版本纳入代码审查及部署检查；禁止后续迁移关闭 RLS、扩大 service role 权限或留下无策略的新租户表。

验收条件：普通业务请求只能访问会话所属单位；新增/修改不能写入其他单位；NULL 历史数据默认不可见；全局名单/热词仍符合共享规则；直接数据库访问、PostgREST 和 service role 配置经过验证；RLS、RPC、API 三层边界的测试结果一致且有真实 PostgreSQL 证据。

本轮仅记录方案，暂不修改 RLS、数据库角色、RPC 或生产权限。
